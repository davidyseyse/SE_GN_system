  第一部分：管理者端操作案例 (Manager / TA Use Cases)
📋 Use Case 1：管理員身份驗證 - 認證攔截機制
對應需求/測試項：FR-1 / 【TC-1-A】
主要參與者：管理者（教師 / 助教）
前置條件：後端服務正常運行，實體環境變數 .env 已配置管理員安全認證資訊。
基本流程：
1. 管理者進入獨立的教師登入頁面 `/teacher/login`；頁面不提供前往學生登入的連結，右上角只顯示教師登入入口。
2. 管理者輸入不相符或錯誤之管理員帳號與密碼。
3. 管理者點擊「登入」按鈕。
4. 後端核心驗證模組對該請求進行安全攔截並拒絕放行。
預期結果：前端介面即時彈出「帳號或密碼錯誤」之錯誤提示，系統限制其進入管理主控台。
📋 Use Case 2：管理員身份驗證 - 正確認證與路由跳轉
對應需求/測試項：FR-1 / 【TC-1-B】
主要參與者：管理者（教師 / 助教）
前置條件：後端服務正常運行，實體環境變數 .env 已配置管理員安全認證資訊。
基本流程：
1. 管理者進入獨立的教師登入頁面 `/teacher/login`。
2. 管理者輸入與 .env 配置完全一致的正確帳號與密碼。
3. 管理者點擊「登入」按鈕。
4. 後端安全驗證通過，並發行安全會話憑證。
預期結果：系統通過身份確認，瀏覽器順利且自動跳轉至「管理主控台面板」。
📋 Use Case 2-A：既有課堂選擇與刪除
主要參與者：管理者（教師 / 助教）
前置條件：管理者已成功登入管理主控台。
基本流程：
1. 系統在課堂下拉選單中只列出目前管理者建立的課堂，且進入頁面時不自動選取。
2. 管理者選取課堂後點擊「重返課堂」，或建立新課堂後由系統自動選取新課堂。
3. 若管理者點擊「刪除課堂」，系統先要求確認，再刪除該課堂及其題目與作答資料。
預期結果：其他管理者無法列出或刪除不屬於自己的課堂；刪除目前課堂後，前端會清除目前課堂狀態。
📋 Use Case 3：雲端表單配置 - 註冊與移除管理
對應需求/測試項：FR-2 / 【TC-2】
主要參與者：管理者（教師 / 助教）
前置條件：管理者已成功登入管理主控台。
基本流程：
1. 管理者於表單配置面板輸入自訂名稱與有效的 Google Sheet ID，點擊「確認新增」。
2. 系統完成持久化後，管理者於列表中精確定位該筆註冊紀錄。
3. 管理者點擊該筆紀錄旁的「刪除」按鈕。
預期結果：新增時，前端列表即時更新映射，後端嵌入式資料庫成功持久化該紀錄；刪除時，該紀錄即時自 UI 列表中移除，後端清除暫存並解除系統與外部該試算表之綁定狀態。
📋 Use Case 4：題目與目標儲存格座標綁定
對應需求/測試項：FR-3 / 【TC-3】
主要參與者：管理者（教師 / 助教）
前置條件：系統至少已成功註冊一個有效的 Google Sheets 配置項目。
基本流程：
1. 管理者於控制台點擊「建立新題目」按鈕。
2. 管理者自表單下拉選單中指名選取已註冊之雲端表單項目。
3. 管理者於目標儲存格座標欄位上手動輸入特定儲存格座標。
4. 管理者點擊「儲存」並返回主頁。
預期結果：題目列表成功新增該項目，資料結構內精確建立表單與目標儲存格之關聯，且初始生命週期狀態由後端指派，於前端渲染為「未開放（灰色）」狀態。
📋 Use Case 5：全域與批次搶答生命週期控制
對應需求/測試項：FR-4 / 【TC-4】
主要參與者：管理者（教師 / 助教）
前置條件：管理者主控台內已預先建立數個不同座標綁定之搶答題目。
基本流程：
1. 管理者針對單一題目獨立點擊「開放搶答」按鈕，隨後點擊「關閉搶答」按鈕。
2. 管理者於控制台頂端控制列點擊「全域重置狀態 (Reset)」功能按鈕並執行確認。
預期結果：點擊開放時，該題全域狀態立即由灰轉綠；點擊關閉時，狀態立即回復灰色，並停止接受新搶答。執行全域重置時，系統將所有題目狀態歸零、清除該回合 Redis 收件序號，並讓全員畫面更新為「未開放（灰色）」狀態；系統不建立或清除 winner lock。
📋 Use Case 6：最快有效答案同步與防重複寫入
對應需求/測試項：FR-5 / 【TC-5】
主要參與者：使用者（學生）、管理者（觀測）
前置條件：多位學生已於開放回合送出搶答，該題綁定目標儲存格座標已配置完成。
基本流程：
1. 使用者於解鎖之答案輸入框中填寫答題內容。
2. 使用者點擊「提交答案」按鈕。
3. 系統依伺服器 `receiptOrder` 判斷目前最低的有效搶答。
預期結果：只有最低有效序號學生的答案會原子寫入資料庫、計入一次成功搶答並同步 Google Sheets API v4；較慢、已取消、已達上限或已有答案的提交會回傳 skipped outcome，且不寫入答案、分數或 Google Sheets。
📋 Use Case 7：已提交答案人為修正與連動同步
對應需求/測試項：FR-5 / 【TC-6】
主要參與者：管理者（教師 / 助教）
前置條件：已有學生成功搶答並完成答案提交，且數據已初次同步寫入 Google Sheets。
基本流程：
1. 管理者進入管理後台之題目列表，精確定位特定學生的提交紀錄欄位。
2. 管理者點擊該列之「修改答案」按鈕。
3. 管理者手動變更答案文字內容，並點擊確定儲存。
預期結果：後台管理介面列表之學生答案內容即時更新反映；同時，後端微服務呼叫 Google Sheets API v4 覆寫外部目標儲存格，將最終文字內容安全同步更新。

📋 Use Case 8：使用者登入校驗 - 非整數格式阻斷
對應需求/測試項：FR-7 / 【TC-7-A】
主要參與者：使用者（學生）
前置條件：使用者開啟瀏覽器並導向獨立的學生登入頁面 `/student/login`。
基本流程：
1. 使用者於登入頁面輸入學號。
2. 使用者於組別欄位輸入非整數文字或含有小數點之文字。
3. 使用者從下拉選單選擇既有課堂，並嘗試點擊「加入課堂」按鈕。
預期結果：前端文字方塊防呆機制主動阻斷非數字之輸入；前後端驗證機制即時攔截該不合規請求，拒絕初始化會話，並於網頁提示錯誤訊息。
📋 Use Case 9：使用者登入校驗 - 標準格式免密碼登入
對應需求/測試項：FR-7 / 【TC-7-B】
主要參與者：使用者（學生）
前置條件：使用者開啟瀏覽器並導向獨立的學生登入頁面 `/student/login`。
基本流程：
1. 使用者於登入頁面輸入正確學號。
2. 使用者於組別欄位輸入符合標準之正整數。
3. 使用者從下拉選單選擇既有課堂；未選課堂時按鈕保持停用。
4. 使用者點擊「加入課堂」按鈕。
預期結果：系統順利完成資料型態校驗，免除密碼驗證程序，使用者畫面順利導向並成功加入搶答大廳。
📋 Use Case 10：狀態機同步與搶答觸發時機
對應需求/測試項：FR-8 / 【TC-8】
主要參與者：全體使用者（學生）、管理者
前置條件：使用者已成功進入搶答大廳，後台題目處於初始階段。
基本流程：
1. 在管理者尚未發布題目時，使用者觀察大廳中該題目的前端按鈕狀態。
2. 當管理者於後端控制台點擊並發送「開放搶答」指令後，使用者觀察大廳按鈕之即時連動。
預期結果：題目未開放時，學生端搶答按鈕為灰色且停用；接收到開放訊號時先顯示可編輯答案欄位，所有答案填寫完整後搶答按鈕才轉為可用。
📋 Use Case 11：高併發非排他搶答與伺服器排序
對應需求/測試項：FR-9 / 【TC-9】
主要參與者：多位使用者（學生）
前置條件：特定題目處於「開放（綠色）」狀態，多位學生同時停留在搶答網頁大廳。
基本流程：
1. 多位使用者先各自填完題目答案，再同時點擊「搶答並送出答案」。
2. 後端為每個合格請求配置單調遞增的伺服器收件序號，前端隨即提交預先填好的答案。
預期結果：所有未達成功上限的學生都可獨立完成答案並搶答，其他同學的按鈕不因先前請求而被鎖住；只有最低有效收件序號的完整答案成功落庫並寫入 Google Sheets。
📋 Use Case 12：不限作答時間、個別取消與下一順位遞補
對應需求/測試項：FR-10 / 【TC-10】
主要參與者：已送出搶答的多位學生
前置條件：系統處於開放回合，已有多筆有效搶答。
基本流程：
1. 學生搶答後可持續填寫答案，系統不顯示倒數，也不會自動逾時。
2. 若最低序號學生不再作答，可主動點擊「取消本次搶答」。
3. 其他學生保留自己的輸入內容並嘗試提交。
預期結果：搶答 attempt 在提交、主動取消或教師重置／關閉回合前保持有效；取消只會停用該學生的 attempt，下一個最低有效序號自然成為可成功提交者。

📋 Use Case 13：跨課堂每組搶答成功次數上限
對應需求/測試項：FR-11 / 【TC-11】
主要參與者：管理者、使用者（學生）
前置條件：同一組別編號已在任一課堂完成一筆最快答案；系統固定上限為一題，老師端不提供設定欄位。
基本流程：
1. 系統只在最快答案成功落庫的同一交易內累加該組跨課堂共用的 `successful_buzz_count`。
2. 同組任何學生在相同或不同課堂再次搶答或提交答案。
預期結果：系統回傳 `SUCCESS_LIMIT_REACHED`，不配置收件序號、不新增搶答／提交／分數紀錄，也不呼叫 Google Sheets；教師成員列表顯示學生組別、該組全域成功次數與固定上限一題。

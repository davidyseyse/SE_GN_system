## Context

本變更要在單一系統內整合課堂建立、學生加入、題目發布、即時搶答、即時作答、計分、排行榜與報表匯出。系統同時面向教師投影控制場景與學生手機瀏覽器場景，因此除了功能完整，還必須優先處理即時同步、搶答一致性、斷線重連與權限隔離。

目前專案內尚未有對應能力，適合直接以新能力方式規劃。由於搶答需要在多人同時提交下保證唯一結果，設計上需要將「畫面狀態同步」與「關鍵競爭判定」分開處理：前者使用 WebSocket 廣播，後者使用後端集中式鎖與原子操作。

## Goals / Non-Goals

**Goals:**

- 提供教師端與學生端完整課堂互動流程。
- 定義清楚的題目狀態機與搶答狀態機。
- 以後端權威時間與原子鎖機制保證第一搶答者唯一。
- 讓作答、統計、分數與排行榜可近即時更新。
- 支援重新連線後的狀態補同步與稽核追蹤。
- 讓規格可直接對應前後端 API、事件與資料模型實作。

**Non-Goals:**

- 不處理原生行動 App。
- 不處理視訊會議、螢幕分享或 LMS 深度整合。
- 不在此變更內設計複雜題庫匯入工具。
- 不在此變更內處理 AI 自動批改或 AI 出題。

## Decisions

### 1. 採用 REST + WebSocket 的混合架構

教師與學生的查詢、建立、編輯、匯出等操作透過 REST API；題目開啟、搶答結果、作答統計、排行榜更新等透過 WebSocket 廣播。這樣可將命令式操作與事件式同步分離，降低狀態混亂。

替代方案是全面使用 WebSocket RPC，但會提高權限控管、錯誤處理與可測試性成本，因此不採用。

### 2. 以後端作為唯一權威狀態來源

所有題目狀態、作答截止、搶答成功與分數計算，都以伺服器保存的狀態為準。前端只做畫面呈現與倒數顯示，不做最終判定。這可避免前端時間差、重送封包或惡意操作造成不一致。

替代方案是以前端本地時間先做 optimistic 判定，但會造成搶答爭議與結果不一致，因此不採用。

### 3. 使用 Redis 原子操作處理搶答競爭

搶答需在高併發下保證只有一位第一名。建議以 Redis `SETNX` 或 Lua script 實作「題目搶答鎖」，寫入第一位成功者、伺服器時間戳與排序序號；資料再異步或同步落庫到 `BuzzRecord`。這可在單一節點或多節點部署下維持一致性。

替代方案是只用資料庫唯一索引搭配交易，但在高頻即時搶答時延遲較高，且排序計算較不直觀，因此 Redis 較適合。

### 4. 題目流程使用明確狀態機

題目狀態定義為 `DRAFT`、`READY`、`BUZZ_OPEN`、`ANSWER_OPEN`、`LOCKED`、`REVIEW`、`PUBLISHED`、`CLOSED`。任何 API 或教師操作都必須通過狀態檢查，避免重複開放、提前作答或錯誤公布。

替代方案是用多個布林欄位表示狀態，但會導致非法組合過多，因此不採用。

### 5. 客觀題自動批改，簡答題進入人工審核

單選、多選、是非題可在提交後立即判定正誤並更新統計；簡答題先保存答案並標記待審，教師評分後再更新分數與排行榜。這可兼顧即時性與可操作性。

替代方案是所有題型都人工批改，但會降低即時回饋價值，因此不採用。

### 6. 重新連線採用快照 + 增量事件

用戶重新連線時，先呼叫 REST 同步目前課堂、題目、個人作答與排行榜快照，再恢復接收 WebSocket 事件。若需要，也可發送 `session.resynced` 事件通知前端完成補同步。

替代方案是只依賴 WebSocket 重播，但會增加事件保存與重播管理複雜度，因此先用快照補同步。

## Risks / Trade-offs

- [高併發搶答造成 Redis 熱點] → 使用短期鍵、最小 payload、限制單題搶答窗口，並保留後端監控。
- [學生網路延遲導致體感不公平] → 明確宣告以伺服器接收時間為準，並保存時間戳與排序供教師查核。
- [大量事件廣播影響教師端畫面穩定] → 對統計更新做節流或批次推送，搶答成功事件仍保持即時單發。
- [簡答題人工批改延後排行榜最終結果] → 在排行榜中標示暫定分數，待人工評分後重新計算。
- [斷線重連造成重複提交] → 所有作答與搶答請求都使用請求 ID 或提交唯一鍵做冪等控制。

## Migration Plan

1. 建立資料表與索引，包括課堂、題目、搶答紀錄、作答紀錄與分數紀錄。
2. 建立登入、課堂、題目、作答、排行榜與報表 REST API。
3. 建立 WebSocket topic、事件契約與 session 驗證。
4. 導入 Redis 搶答鎖與排序策略。
5. 完成教師端主控台與學生端互動畫面。
6. 加入統計、報表與匯出功能。
7. 進行多人併發搶答、斷線重連與權限測試。

回滾策略：

- 關閉新課堂互動入口並停用 WebSocket topic。
- 保留資料表但停止對外操作。
- 若 Redis 搶答服務異常，教師端不可開啟搶答模式。

## Open Questions

- 學生是否允許匿名暱稱模式，或必須綁定校務帳號。
- 錯答扣分是否為課堂級設定、題目級設定，或兩者都支援。
- 排行榜是否需要支援分組模式與隊伍總分。
- 報表匯出格式是否只需要 CSV，或必須同時支援 Excel 原生格式。

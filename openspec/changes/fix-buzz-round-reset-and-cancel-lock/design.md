## Context

現行搶答鎖存於 Redis，成功與失敗的搶答紀錄則永久存於 `buzz_records`。教師重置與學生取消鎖定只刪除 Redis winner key；教師重置還會刪除 sequence key。資料庫仍以題目為範圍限制單一成功勝者，答案提交也以題目與學生判定重複。

學生端使用題目 ID 保存本地勝者、答案草稿與已提交狀態。收到 `BUZZ_RESET` 或 `BUZZ_CANCELLED` 時只清除本地勝者，因此上一輪的已提交狀態會繼續停用輸入框與提交按鈕。

## Goals / Non-Goals

**Goals:**

- 讓教師重置後的重新搶答成為不受舊資料影響的新回合。
- 讓未提交答案的勝者可以放棄答題權，並讓下一位勝者正常作答。
- 在前端與後端同時禁止已提交答案的勝者取消鎖定。
- 保留歷史搶答與作答資料供稽核、報表及追蹤。
- 避免舊回合的即時事件污染新回合 UI。

**Non-Goals:**

- 不改變題目內容、計分規則或教師批改流程。
- 不允許學生在提交答案後撤回或刪除答案。
- 不讓學生取消其他學生的搶答鎖。
- 不將教師重置改成自動重新開放；重置後仍需教師再次開放搶答。

## Decisions

### 1. 使用持久化回合識別

每個搶答題保存目前回合識別；每次由非開放狀態切換為 `BUZZ_OPEN` 時建立新回合。搶答紀錄與作答紀錄關聯至該回合。

選擇持久化回合識別，而不是在重置時刪除資料，原因是現有需求要求搶答順序可稽核，且舊答案可能已同步至外部表單。

### 2. 勝者唯一性以回合為範圍

資料庫限制調整為每個 `question_id + round_id` 最多一筆有效成功勝者。取消鎖定會將該勝者標示為 `CANCELLED`／非有效，而不是刪除紀錄；同一回合可因此產生下一位有效勝者。

搶答序號以回合為範圍。取消鎖定不重置序號，使同一回合內的搶答歷史仍可排序。教師重置結束回合；下一次開放建立新序號範圍。

### 3. 教師重置與學生取消具有不同語意

- 教師重置：結束目前回合、題目回到 `READY`、清除目前 Redis 鎖；不立即重新開放。
- 學生取消：僅允許目前有效勝者在尚未提交時使用；放棄答題權後題目保持 `BUZZ_OPEN`，立即允許其他學生搶答。

### 4. 後端是取消資格的最終判定者

取消端點必須驗證：

1. 題目仍處於 `BUZZ_OPEN`。
2. 呼叫者是目前回合的有效勝者。
3. 該勝者在目前回合尚未提交答案。

任一條件不符時拒絕請求。前端隱藏按鈕只是操作提示，不能取代後端驗證。

### 5. 學生端狀態以題目與回合為範圍

即時事件包含 `questionId` 與 `roundId`。學生端只套用目前回合的 winner、cancel、reset 與 submission 狀態。

- `BUZZ_CANCELLED`：清除取消者的未提交草稿與本地勝者狀態，但題目仍可搶答。
- `BUZZ_RESET`：清除該題目前回合的勝者、草稿與已提交 UI 狀態；題目顯示未開放。
- 提交成功：標記目前題目與回合為已提交，並隱藏取消鎖定。

### 6. 舊資料保留但不參與目前回合判定

查詢目前勝者與重複提交時必須限定目前 `roundId`，不可再從題目的全部歷史紀錄選取最大 `receiptOrder`。報表可列出所有回合，並標示回合與取消結果。

## Risks / Trade-offs

- 資料庫 migration 需要替既有資料建立可接受的 legacy round，並更新唯一索引。
- 若 Redis 鎖成功但資料庫寫入失敗，需釋放鎖或使用一致性補償，避免幽靈勝者。
- 舊版 WebSocket client 不認識 `roundId`；事件欄位應採向後相容新增，部署時仍應優先更新後端再更新前端。
- 外部 Google Sheets 目前可能沒有回合欄位；本變更只確保新回合作答可同步，不改變既有表格格式。

## Migration Plan

1. 新增搶答回合資料或等價欄位，為既有 buzz/submission 指派 legacy round。
2. 將唯一勝者及 submission 唯一性調整為回合範圍。
3. 更新後端開放、重置、搶答、取消與提交流程。
4. 更新即時事件 payload 與學生端狀態管理。
5. 執行 migration、API 整合測試與前端測試。
6. 若需回滾，先回滾應用程式；保留新增回合欄位，避免破壞已寫入的歷史資料。

## Open Questions

- 無。已確認提交前可以取消、提交後不能取消；教師重置後回到未開放，學生取消後則立即維持開放。
